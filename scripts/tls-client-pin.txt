# The native TLS binary the gateway runs, recorded by digest.
#
# WHY THIS IS RECORDED AND NOT PINNED, WHICH IS AN ADMISSION, NOT A DESIGN.
#
# `tls-client-node@0.2.0` fetches a platform `.so` from the `bogdanfinn/tls-client`
# GitHub releases at image-build time and resolves the version THEN, from
# `/releases/latest`, with nothing pinning it. A third party therefore decides
# which binary runs inside this deployment's gateway, and the decision is made
# on the day the image is built rather than on the day the code is reviewed.
#
# We cannot pin it from here. The lever exists -- the package's postinstall
# reads `TLS_CLIENT_VERSION` -- but the `RUN` that invokes it is at
# omniroute/Dockerfile:111, and every `ARG` in that file is declared at 135,
# 140, 152 and 169, all AFTER it. A `--build-arg` has nothing to bind to, and
# `env_file:` is runtime, not build time. Adding the ARG means editing a
# squashed subtree that the next `git subtree pull` silently reverts, which
# CLAUDE.md forbids for exactly that reason. It is proposed upstream instead:
# upstream-patches/omniroute-pin-tls-client.patch.
#
# So this file does the one honest thing left: it records what is actually
# running, and `king-audit.sh` J-4 compares the running container against it.
# A future build that quietly pulls a different binary cannot be PREVENTED
# here, but it becomes VISIBLE the next time the audit runs. Claiming the pin
# is under control would be worse than admitting it is not.
#
# HISTORY, because this binary has a five-day hole in it.
#
#   2026-06-08  v1.15.1 published, both naming schemes.
#   2026-08-27  omniroute:base built -> tls-client-linux-ubuntu-amd64-1.15.1.so
#               (carries CVE-2025-68121, GHSA-h355-32pf-p2xm, medium, CVSS 4.8:
#               a crypto/tls Config whose ClientCAs/RootCAs are mutated between
#               handshakes may resume a session it should have rejected.)
#   2026-09-02  v1.16.0 published with the `xgo` asset names ONLY. Every build
#               of this image fails at the Dockerfile:111 guard, correctly.
#   2026-09-07  upstream re-uploads the legacy `ubuntu`/`alpine`/`arm64` names
#               into the same release at 22:42Z. The break ends, with no change
#               in this repo and none in tls-client-node.
#   2026-09-10  five bounded rebuild attempts on this VPS, all failed on
#               memory.
#   2026-09-11  three more, also failed. The host cannot build this image while
#               serving the gateway; see WHY THE REBUILD WAS ABANDONED below.
#               The gateway was instead cut over to a PATCH LAYER carrying the
#               digest below -- scripts/king-tls-patch.sh --apply. Container
#               e482159a1301 -> 963966991bbc, healthy in 6s, 7 API keys intact,
#               J-4 and J-5 green. CVE-2025-68121 is closed on this deployment.
#
# SO WHAT IS RUNNING IS NOT WHAT THE DOCKERFILE BUILDS. omniroute:base is now
# the 2026-08-27 image plus one layer that replaces this binary. Everything
# else in it -- including its OS packages -- is still from 2026-08-27. That is
# the cost of the stopgap and the reason this file says "stopgap": the next
# real rebuild supersedes it and should simply overwrite omniroute:base.
#
# WHY THE PREVIOUS RED WAS NOT AN EMERGENCY, MEASURED RATHER THAN ASSUMED.
#
# The .so is loaded lazily, on first use of a provider that does TLS
# impersonation. omniroute/Dockerfile:101 names them: chatgpt-web, claude-web,
# grok-web, lmarena, perplexity-web. Measured on the running gateway
# 2026-09-10:
#
#   provider_connections   ->  agy, ollama-local, openrouter, tavily-search
#   /proc/1/maps           ->  no tls-client .so mapped, 3h into the process
#   find /app -name '*.so' ->  exactly one copy, never opened
#
# So the vulnerable code does not execute in this configuration. Combined with
# the advisory's own numbers -- GHSA-h355-32pf-p2xm, medium, CVSS 4.8, attack
# complexity HIGH, confidentiality and integrity impact LOW -- that is a fine
# reason to wait for a maintenance window and a terrible reason to forget.
#
# "Safe because nothing uses it" is a CONDITION. An unwatched condition is what
# every entry in docs/king-mistakes.md turns out to be, so the condition is
# asserted instead of trusted: J-5 goes red the moment one of those five
# providers is configured while the running binary is still the wrong one.
#
# WHY THE REBUILD WAS ABANDONED, WITH THE NUMBERS, FOR WHOEVER TRIES NEXT.
#
# On 2026-09-10 this section said a patch layer was "deliberately not done"
# because it fixes the artefact rather than the build. That reasoning assumed
# the build was achievable. Eight attempts say it is not, on this host, and a
# choice between two options only one of which exists is not a choice.
#
#   turbopack  SIZES ITSELF TO THE CGROUP and then exceeds it:
#                cage 3584 MB -> killed at 3.11 GB   (87% of the cage)
#                cage 4608 MB -> killed at 3.99 GB   (87% of the cage)
#              Raising the cage 29% raised its appetite 28%. There is no cage
#              this host can afford that it will not fill.
#              omniroute/Dockerfile:131 says why: OMNIROUTE_BUILD_MEMORY_MB
#              caps only the V8 heap, and turbopack compiles in native Rust
#              memory outside it.
#   webpack    IS bounded by --max-old-space-size, and needs more than 4096 MB:
#                "FATAL ERROR: Ineffective mark-compacts near heap limit",
#                with no kernel OOM at all.
#              build-next-isolated.mjs:194 raised its own default to 8192 for
#              this reason, noting 4096 "brushed the ceiling".
#
# Swap does not help: V8 throws at its own ceiling rather than spilling, which
# is why a 3 GB cgroup swap allowance went untouched.
#
# This host has ~5.7 GB once activepieces, codegraph-serve and ollama are
# stopped, and must keep a 1.16 GB gateway alive. omniroute-smoke builds the
# same commit green on a GitHub runner, so the Dockerfile is fine; the host is
# the constraint, and the real fixes are a bigger machine, a build moved off
# this box, or the upstream ARG in
# upstream-patches/omniroute-pin-tls-client.patch.
#
# The upstream release publishes its own digest, so the value below was checked
# against the source and not merely observed locally:
#
#   GET /repos/bogdanfinn/tls-client/releases/tags/v1.16.0

#     size   17379216
